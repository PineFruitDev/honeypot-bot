# Honeypot Bot: public multi-guild readiness audit and hosting plan (Codex) (Grok Bot)

This is the historical pre-implementation audit. See [the release checklist](release.md) for the integrated changes, remaining limits, and deployment status.

Audit date: 2026-11-01. Source baseline: `6dd87b058d5c62ff71e43e5e0c747171b0e98f97`.

**Decision: multi-guild foundations exist; broad public rollout should wait for the fixes below.** This is a static, docs-only review, not runtime acceptance or a security certification. No installs, bot execution, credential inspection, external documentation lookup, portal changes or deployment were performed. The initial `gh pr list --state open` returned no open PRs. Provider pricing, account capacity and current Discord platform limits remain unverified under the network restriction. Function names below identify the reviewed code precisely.

## Per-guild configuration and state

**Current:** [GuildConfigStore.ts](../src/services/GuildConfigStore.ts), `init`, `setTrap`, `patchGuild`, `recordCatch` and `removeGuild`, key settings by guild ID in `DATA_DIR/guilds.json`. A singleton serializes writes within one process; recent catches are capped at 50 per guild, with separate lifetime totals. [Bot.ts](../src/core/Bot.ts), `handleMessage`, matches both guild and channel. `reconcileOnBoot` clears missing trap channels but retains departed-guild records.

**Gaps:** Direct whole-file writes are not crash atomic; parse/read errors start with empty state and later writes can replace the original data. Persistence errors are logged and swallowed, so success can mean memory-only configuration. Serialization does not coordinate multiple processes or concurrent setup/remove workflows. No schema validation, retention deadline, departure cleanup or supported backup/restore procedure exists.

**Concrete fix:** Initially enforce one process and a persistent volume. Validate/version state; distinguish a missing file from corrupt/unreadable storage and stop configuration mutations on the latter. Write via temporary file and atomic rename, preserve a known-good backup, surface failed persistence, and drain writes at shutdown. Serialize guild mutations. Add departure retention/deletion policy and backup restore drills. Before replicas/shards, migrate to transactional storage keyed by guild ID with revisions and unique event/action IDs. Prove two-guild isolation, disk failure, corrupt file, restart and competing mutations in tests.

## Least-privilege permissions and gateway intents

**Current:** [Bot.ts](../src/core/Bot.ts), constructor, requests only `Guilds` and `GuildMessages`; it detects message presence without reading content. Neither Message Content, Guild Members nor Presence privileged intent is requested. [HoneypotCommand.ts](../src/commands/HoneypotCommand.ts) sets administrator default command permissions and guild-only runtime behavior. [Command.ts](../src/core/Command.ts), `validate`, supports bot permission checks; [EnforcementService.ts](../src/services/EnforcementService.ts), `missingPermissionsFor`, checks selected action permissions.

**Gaps:** Guild-level permissions do not prove channel overwrite access or target role hierarchy. The README invite checklist omits Manage Messages for deleting other users' posts, Read Message History for conversion checks and Embed Links for embeds. Default command permissions alone are not a runtime administrator check. Ban Members remains necessary even for timeout/quarantine because young accounts escalate to bans and buttons request softbans.

**Concrete fix:** Define the proposed installation scopes as `bot` and `applications.commands`; do not request Administrator for the bot. Full current functionality requires View Channel, Send Messages, Embed Links, Read Message History, Manage Messages in relevant channels, Manage Channels for provisioning, Manage Roles for hide/quarantine roles, Ban Members for bans/softbans/escalation, and Moderate Members for timeout mode. Kick Members is unnecessary for the implemented softban. Scope channel grants to trap/log channels where feasible; quarantine currently touches all manageable channels. Validate effective channel permissions and role hierarchy at setup and before actions. Enforce the intended operator authorization at runtime and explicitly constrain registration contexts to guild installation. Keep the two existing intents; verify platform eligibility before release without enabling privileged intents by default.

## Rate limits and bounded work

**Current:** Normal operations use discord.js. [DiscordApi.ts](../src/services/DiscordApi.ts) uses raw fetch for ban/unban/ban-status calls; `softbanUnban` attempts three unbans with a five-second wait budget and a final status check. [CommandRegistrar.ts](../src/services/CommandRegistrar.ts) fingerprints registrations to avoid unchanged writes. Each catch can delete, moderate, DM, report and refresh the sticky message.

**Gaps:** No shared limiter coordinates raw fetch with discord.js, no per-guild fairness, action deduplication or bounded concurrency. Ban requests do not retry 429s; fetch calls lack deadlines. The unban wait uses `min(retry_after, remaining budget)`, so a long requested wait can cause an early retry. Sticky refreshes can race and amplify a flood.

**Concrete fix:** Centralize REST scheduling with route/global cooldowns, bounded queues and per-guild fairness. Honor the complete server retry delay; if it exceeds the immediate budget, persist a recovery job instead of retrying early. Add request deadlines, bounded jittered retries for transient failures and terminal handling for permission errors. Deduplicate event IDs and serialize each guild/member action; coalesce sticky updates and rate-limit setup/hide operations. Test a burst across two guilds, long 429 waits, global throttling, stalled fetch and duplicate events. Measure throughput before choosing capacity; do not infer unlimited guild scale from keyed storage.

## Abuse safety and moderation correctness

**Current:** [EnforcementService.ts](../src/services/EnforcementService.ts), `isExempt`, protects the owner, this bot and configured users/roles. Other bots are intentionally eligible. Accounts younger than seven days escalate to bans; kick means ban with seven-day message purge followed by unban. [HoneypotCommand.ts](../src/commands/HoneypotCommand.ts), `refuseUnsafeConversion`, rejects system/rules channels and a sample of 20 recent messages containing human activity. [HoneypotService.ts](../src/services/HoneypotService.ts) tracks ownership of hide overwrites.

**Gaps:** Failed history fetch permits conversion; failed member lookup can bypass role exemptions. Deletion occurs before exemption checking. Button handling recognizes custom IDs without checking the configured channel/current sticky message, so stale components remain actionable. A button click can permanently ban a young account despite the README's recoverable-misclick framing. Stats buttons expose recent catch identities to any presser. Quarantine role denies are not proof of containment against other role/member allows; channel overwrite failures are swallowed and newly created channels are not reconciled continuously.

**Concrete fix:** Refuse conversion when safety history cannot be checked; prefer a dedicated new channel. Require explicit confirmation of purge, escalation and button consequences; add a per-guild pause and an observation-only trial mode. Resolve exemptions before deletion/moderation and stop when required membership evidence is unknown. Bind buttons to the active guild/channel/message and deduplicate interactions. Restrict detailed catch history to authorized staff; minimize public stats. Verify quarantine effective permissions, repair new channels, and report partial containment truthfully. Add regression cases for stale buttons, lookup failures, young-account clicks, conflicting overwrites and setup/remove races.

## Errors, recovery and operations

**Current:** [Bot.ts](../src/core/Bot.ts) catches command/message failures and replies ephemerally to command errors. [DiscordApi.ts](../src/services/DiscordApi.ts) preserves unban status details and checks ban state after exhausted retries. [EnforcementService.ts](../src/services/EnforcementService.ts) reports failed actions and treats DMs as best effort. [Environment.ts](../src/services/Environment.ts) validates required configuration; [Logger.ts](../src/services/Logger.ts) provides timestamped logs. [index.ts](../src/index.ts) handles signals and startup failure.

**Gaps:** A crash between ban and unban can leave a permanent ban without a durable recovery record. Unknown ban status is conservatively flagged but is not proof of a remaining ban. Storage and some channel errors disappear into logs; asynchronous ready reconciliation has no enclosing error boundary. Shutdown destroys the client and exits without explicitly draining actions or persistence. Logger accepts arbitrary errors; environment diagnostics include a masked token representation. No health/readiness surface or alert policy exists.

**Concrete fix:** Persist softban intent and phases before mutation, reconcile pending jobs at startup and alert staff on unresolved/unknown outcomes. Keep success, failure and unknown separate in reports/DMs. Catch ready-handler failures per guild so one failure does not block registration. Defer role-changing interactions before REST work. Drain bounded in-flight work on shutdown and preserve unfinished jobs. Log allowlisted error fields with correlation/guild/action IDs, never credential fragments, request headers or raw environment objects. Add disk-failure, lost-permission, disconnect, restart-mid-softban and restore acceptance checks plus alerts for pending unbans, write failures and sustained 429s.

## Slash command registration: global versus guild

**Current:** [commands/index.ts](../src/commands/index.ts) supplies the command list. [CommandRegistrar.ts](../src/services/CommandRegistrar.ts), `createRestApi`, bulk overwrites global commands via `Routes.applicationCommands(clientId)`. Successful registration persists a payload/application fingerprint in `commands.json`; unchanged boot registration is skipped. [index.ts](../src/index.ts) registers after ready reconciliation unless `REGISTER_ON_BOOT` is disabled. [register.ts](../src/register.ts) forces global registration and exits nonzero on failure.

**Gaps:** No guild registration target or isolated staging path. A new boot payload can change commands for all installations; bulk overwrite can remove commands omitted from the registry. Local fingerprints cannot detect external changes. Multiple instances can register concurrently. Current platform quotas/propagation behavior were not checked.

**Concrete fix:** Add an explicit guild/global registration target, a test guild ID and `applicationGuildCommands` route for staging, with fingerprints scoped to application plus target. Use a separate staging application where possible. Test guild commands first, then make global registration an operator-controlled release step with one owner and a reviewed payload diff. Disable automatic production registration once that workflow exists. Remove obsolete test-guild registrations deliberately to avoid shadowing global commands; retain the previous payload for rollback. Verify current registration quotas before release rather than relying on source comments.

## Hosting plan

**Proposed first host: Apollo, conditional on confirming an always-on Node process and durable storage.** Apollo's actual plan, capacity, price and operational features are not established by this repository. This is an architecture comparison, not a provider quote.

| Concern | Apollo: existing Node gateway bot | Cloudflare Worker: interactions endpoint |
| --- | --- | --- |
| Runtime fit | Keep discord.js and the persistent Discord Gateway session; message traps and buttons retain the existing event model. Confirm outbound WebSocket support and restart policy. | Rewrite command/button handling as HTTP requests with signature verification, PING handling, timely acknowledgement/deferred response and replay protection. The current Node client/filesystem architecture is not a drop-in Worker deployment. |
| Message traps | Gateway receives `MessageCreate`, the core trigger in `Bot.ts`. | An interactions endpoint receives commands/components, not arbitrary guild messages. Endpoint-only hosting loses the message trap. Retaining it requires a separate gateway service, or a separately validated stateful gateway design. WebSocket support alone does not solve Gateway heartbeats, resume and session ownership. |
| Cost | Unknown monthly quote. Budget compute/RAM, persistent disk, backups, logs and operator time; existing capacity is not proof of zero incremental cost. | Unknown current pricing. Model request/CPU use, D1 or Durable Objects storage/operations, queues and logs. A hybrid also pays for a gateway host. A free allowance is not a production cost guarantee. |
| State | One writer and persistent `DATA_DIR`; backup and restore both guild and registration state. Move to transactional storage before replicas. | Replace local JSON with transactional persistent state (candidate D1/Durable Objects); use durable recovery jobs and deduplication. Define gateway/endpoint ownership so they cannot race actions. |
| Secrets | Inject bot token via host secret facility; keep application ID separate. Verify access controls, redacted logs and token rotation procedure. No secrets in images or repository. | Store bot token in Worker secrets if REST moderation is needed; use application public key for signed request verification (the public key is not secret). Keep staging/production credentials and bindings separate. |
| Operations | Supervise one instance, controlled restarts, readiness after storage/login, alerts, drain and rollback. Confirm Node compatibility and host support ownership. | Maintain endpoint authentication, latency budgets, durable background work, migrations, observability and rollback; hybrid adds gateway monitoring and coordination. No Worker implementation is present. |

Before choosing, Sky should obtain Apollo's actual quote/limits and the current Worker pricing schedule, then estimate monthly cost from measured guild count, catch volume, REST fan-out, retained records and logs. Compare total cost including maintenance hours. Cost this audit: unknown. Do not choose an interactions-only rewrite while promising message-based detection.

Release sequence after separate implementation authorization: fix persistence and moderation safety; prove isolated two-guild behavior and recovery in staging; validate least-privilege installation and command registration; confirm hosting/restore procedures; then seek public launch approval. Existing tests in [test](../test) cover store, softban, escalation and hide-role behavior, but were not run in this docs-only audit and do not establish hosted readiness.
